# 0011 — Use one deployment and one database per client

- **Status:** Proposed
- **Date:** 2026-10-16
- **Deciders:** Humberto
- **Supersedes:** [0002](0002-use-shared-schema-multi-tenancy-with-rls.md), [0003](0003-use-global-identity-with-tenant-memberships-and-rbac.md)

## Context
ADR 0002 and ADR 0003 assumed Shopkeeper would become a multi-tenant SaaS: many merchants in one application and one database. That premise was wrong. Shopkeeper is a **reusable template** (Go backend + Next.js frontend) for client jobs. Each client gets an isolated copy: its own server, its own database, its own application. Data of two clients never share a database or a process.

The multi-tenant design protects against a risk that does not exist here, and it costs complexity everywhere: `tenant_id` in every key and index, composite foreign keys, RLS policies and a guard test, `InTenantTx` around every query, memberships and a tenant-selection step at login, a provisioning command, and two-tenant fixtures in every repository test.

What is still needed:
- Staff rules differ between clients (the clerk sells but never sees cost; discount ceiling per role), so roles and permissions must stay configurable.
- Each installation needs its own business data (legal name, CNPJ, time zone, branding, pricing defaults).
- Append-only tables (`audit_log`, `stock_movements`) must stay protected from the application role.

## Decision
1. **One deployment = one client = one PostgreSQL database.** No `tenant_id` column, no RLS, no `app_current_tenant()`, no `InTenantTx`.
2. Tables use `id uuid PRIMARY KEY` (UUIDv7 generated by the app) and plain foreign keys.
3. The client's business data lives in a **singleton** `business` row (profile + settings), created by a `setup` command when the system is installed, together with the default location, the system roles and the first owner.
4. **Identity:** `users` belong to the installation. Each user has one `role_id`. Roles keep **permission-based RBAC** (`permissions`, `roles`, `role_permissions`); use cases check permissions, never role names. System roles `owner` and `clerk` are seeded; BR-03 becomes "at least one active user with the owner role".
5. Two database roles stay: `shopkeeper_migrator` owns the tables and runs migrations; `shopkeeper_app` is not the owner, so `REVOKE UPDATE, DELETE` keeps `audit_log` and `stock_movements` append-only.
6. Per-client differences go in configuration (env vars, the `business` row, seeded data), not in edits to the core, so fixes in the template can flow to every client copy.

## Alternatives considered
| Option | Pros | Cons |
|---|---|---|
| One deployment and database per client (chosen) | Simplest schema, queries and tests; isolation by infrastructure; each client can be upgraded, backed up and moved on its own | No shared operation across clients; each deploy is upgraded separately |
| Keep shared-schema multi-tenancy (ADR 0002) "just in case" | Ready if a SaaS is ever wanted | Cost in every table, query and test for a model that will not be used |
| Schema or database per tenant inside one application | Strong isolation | Same unused multi-tenant machinery (tenant routing, pools, migrations per tenant) |
| Fixed roles in code instead of RBAC tables | Simplest identity | A client with different staff rules needs a code change in its copy |

## Consequences
- Positive: no tenant concept in the code; repositories and tests are plain; the login has no tenant-selection step.
- Positive: a client's copy can be backed up, restored or moved without touching other clients.
- Negative: there is no single place to see or upgrade all clients; each deploy runs its own migrations.
- Negative: the `business` singleton must be created before the API serves requests (the `setup` command; the API should fail readiness while it is missing).
- Follow-ups: rewrite the data model, architecture docs and Phase 1 issues (specs 008–010). If a real SaaS is ever wanted, that is a new ADR and a migration that adds `tenant_id`; nothing is prepared for it now.
